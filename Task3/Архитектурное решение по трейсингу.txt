ЗАДАНИЕ 3. АРХИТЕКТУРНОЕ РЕШЕНИЕ ПО ТРЕЙСИНГУ
Компания «Александрит». Архитектор: В. Цепляев.

Цель: дать команде инструмент, который показывает, что происходило с заказом и
где он находится сейчас, чтобы находить, где заказ «сломался», завис или потерялся.
Опирается на Задание 1 (инициатива I-1) и стек мониторинга из Задания 2.

======================================================================
1. АНАЛИЗ СИСТЕМЫ В КОНТЕКСТЕ ТРЕЙСИНГА
======================================================================
Заказ проходит сквозь три системы и очередь, меняя статусы. Именно на границах
между компонентами он и «теряется». Разберём, где заказ может сломаться/зависнуть.

Сквозной путь заказа и точки риска (что покрываем трейсингом):

  [B2C]     Customer → Internet Shop → Shop API → Shop DB
            (INITIATED, FILE_UPLOADED, SUBMITTED; загрузка 3D в S3)
            Риск: загрузка 3D в S3 (таймаут/ошибка), запись в Shop DB.

  [Партнёр] API user → MES API (публичный API) → создание заказа
            Риск: партнёрский трафик конкурирует с операторами (B3); ошибки
            на публичном эндпоинте не видны Яндекс.Метрике.

  ГРАНИЦА 1: Shop API/MES API → RabbitMQ → потребитель  (расчёт цены)
            Риск №1: здесь заказы теряются. Сообщение опубликовано, но не
            доставлено/не обработано/обработано дважды. PRICE_CALCULATED.

  [MES]     MES API считает цену (CPU-heavy) → MES DB, публикует статус в очередь
            Риск: долгий/упавший расчёт; сообщение о статусе не ушло.

  ГРАНИЦА 2: MES → RabbitMQ → CRM API  (создание/подтверждение заказа в CRM)
            Риск №2: «заказ создаётся в CRM через сообщение из очереди от MES».
            Если сообщение потеряно — MANUFACTURING_APPROVED никогда не наступит,
            заказ зависает навсегда. CRM API пишет и в Shop DB (связность).

  [MES]     Оператор: MANUFACTURING_STARTED → COMPLETED → PACKAGING → SHIPPED
            Риск: заказ не взят в работу (не виден в медленном дашборде, C1).

  ГРАНИЦА 3: транспортная компания / CRM → CLOSED
            Риск: сообщение о доставке не обработано, заказ «завис» перед закрытием.

Системы/контейнеры, которые СЛЕДУЕТ покрыть трейсингом (выделены на схеме):
  - Internet Shop (фронт, RUM) — начало трейса на стороне пользователя;
  - Shop API, CRM API, MES API — все переходы и обращения к БД/S3/очереди;
  - RabbitMQ — критично: пробрасывать trace-context в заголовках сообщений
    (traceparent по W3C Trace Context), чтобы трейс не рвался на границе очереди;
  - обращения к Shop DB, MES DB, 3D files storage — как дочерние спаны.
Приоритет №1 — именно ГРАНИЦЫ через RabbitMQ (границы 1 и 2): там теряются заказы.

======================================================================
2. ДАННЫЕ, КОТОРЫЕ ДОЛЖНЫ ПОПАДАТЬ В ТРЕЙСИНГ
======================================================================
Стандартные поля спана (по OpenTelemetry):
  - trace_id — единый идентификатор всего пути заказа (сквозной);
  - span_id / parent_span_id — иерархия операций (waterfall);
  - service.name — какой сервис (shop-api, crm-api, mes-api, ...);
  - operation / span.name — операция (POST /orders, calc_price, publish/consume);
  - start_time, end_time, duration — тайминги (где долго);
  - span.kind — server | client | producer | consumer (важно для границ очереди);
  - status — ok | error + сообщение об ошибке/стек (где сломалось).

Атрибуты, специфичные для домена (теги/attributes спана):
  - order.id — КЛЮЧЕВОЙ: поиск всего пути конкретного заказа;
  - order.status — статус на момент операции (INITIATED … CLOSED);
  - order.channel — b2c | partner (+ partner.id при небольшом числе партнёров);
  - messaging.system=rabbitmq, messaging.destination (queue/topic),
    messaging.message_id — для сопоставления publish↔consume на границе очереди;
  - db.system, db.operation (без текста запроса и без PII);
  - http.method, http.route (шаблон, не raw URL), http.status_code;
  - env (dev|release|prod), instance/host, version (для сопоставления с релизом).

Чего в трейсинг класть НЕЛЬЗЯ (безопасность/приватность, см. раздел 6):
  - персональные данные клиента (ФИО, адрес, контакты, платёжные данные);
  - содержимое 3D-файлов, токены/секреты, тела запросов целиком.
  Только идентификаторы (order.id), а не сами чувствительные данные.

======================================================================
3. МОТИВАЦИЯ
======================================================================
Почему трейсинг и что он даёт компании:

  - Метрики (Задание 2) отвечают «ЧТО и насколько плохо» (растёт очередь, растут
    ошибки), но НЕ отвечают «ГДЕ именно и ПОЧЕМУ завис конкретный заказ».
    Трейсинг отвечает на «где заказ сейчас и что с ним было» — ровно то, что просит
    бизнес. Он связывает разрозненные системы (магазин/MES/CRM/очередь) в единую
    сквозную картину пути одного заказа.
  - Позволяет по номеру заказа за секунды показать его waterfall и точку, где он
    остановился (не дошло сообщение в CRM, упал расчёт цены и т.п.) — вместо
    ручного разбора логов трёх систем.
  - Прекращает «тихую» потерю заказов: видно разрыв publish↔consume на очереди.

Метрики решения, на которые влияет внедрение трейсинга:

  Технические:
   1) MTTR (среднее время локализации/устранения инцидента с заказом) — резко
      снижается: путь заказа виден сразу, не нужно вручную коррелировать логи.
   2) Доля «потерянных» сообщений на границах очереди (publish без consume) —
      становится измеримой и стремится к нулю.
   3) p95/p99 длительности этапов заказа (расчёт цены, обработка сообщения) —
      находим и убираем узкие места.

  Бизнесовые:
   4) Доля заказов, нарушивших SLA (3 недели), и время «зависания» на этапе —
      снижаются, т.к. проблемы видны и чинятся до жалобы клиента.
   5) Количество жалоб «не получил заказ» и потерянных контрактов — снижается
      (проактивная реакция вместо реакции на звонок клиента).

======================================================================
4. ПРЕДЛАГАЕМОЕ РЕШЕНИЕ
======================================================================
4.1. Технологии и подход
  - Стандарт инструментирования: OpenTelemetry (OTel) — вендоронезависимо,
    единый формат для Java (Spring, Shop/CRM API) и C# (MES API), а также для
    фронтенда (JS SDK). Контекст распространяется по W3C Trace Context (traceparent).
  - Транспорт: OTLP от сервисов → OpenTelemetry Collector (единая точка приёма,
    батчинг, сэмплирование, обогащение, экспорт).
  - Бэкенд трейсинга: Jaeger (UI, поиск по trace_id/order.id, waterfall). Как
    альтернатива — Grafana Tempo (дешевле по хранению, интеграция с Grafana из
    Задания 2). Выбор фиксируем на этапе PoC.
  - Хранилище спанов: Elasticsearch/Cassandra (для Jaeger) или объектное
    хранилище (для Tempo), с ограниченным retention (напр. 7–14 дней).

4.2. Что внедрить/доработать (компоненты)
  Новые компоненты (на схеме — КРАСНЫМ):
   - OpenTelemetry Collector — приём OTLP, обработка, экспорт.
   - Tracing Backend (Jaeger) — хранение и визуализация трейсов.
   - Trace Storage — хранилище спанов.
  Доработки существующих компонентов:
   - Shop API, CRM API (Spring): подключить OTel Java-агент (auto-instrumentation
     HTTP/JDBC/AMQP) + ручные спаны на бизнес-операции (смена статуса, расчёт).
   - MES API (C#): OpenTelemetry .NET SDK, инструментирование HTTP/DB/AMQP.
   - Internet Shop (Vue): OTel JS для трейсов из браузера (по желанию, RUM).
   - RabbitMQ producer/consumer: проброс traceparent в заголовках сообщений —
     БЕЗ этого трейс рвётся на границе очереди (ключевой пункт).
   - Добавить order.id как атрибут спанов во всех сервисах.

4.3. Сэмплирование
  - На старте — tail-based sampling на Collector: 100% ошибочных и «медленных»
    трейсов + процент нормальных. Так не раздуваем хранилище, но не теряем
    проблемные заказы (именно они нам и нужны).

4.4. Схема (диаграмма C4, новые элементы — КРАСНЫМ)
  Файл: Task3/jewerly_c4_tracing.drawio
  На схеме добавлены: OpenTelemetry Collector, Tracing Backend (Jaeger),
  Trace Storage, роль Support/Engineer (смотрит трейсы), связи «OTLP спаны» от
  Shop API / CRM API / MES API / Internet Shop к Collector, экспорт в Jaeger,
  запись в Trace Storage, а также пометка о пробросе trace-context через RabbitMQ.

4.5. ДОПОЛНИТЕЛЬНО: авто-мониторинг прохождения заказа и алертинг
  Идея: из данных трейсинга автоматически детектировать застрявшие заказы и
  нарушения SLA, не дожидаясь ручного просмотра трейсов.
  Реализация (на схеме — ЗЕЛЁНЫМ):
   - Span Metrics / Tail Sampling (connector в OTel Collector): превращает спаны
     в метрики этапов заказа (длительность и число переходов по статусам, разрывы
     producer→consumer) и оставляет проблемные трейсы.
   - Order Journey Monitor (Prometheus + правила): хранит эти метрики; правила
     детекции — «нет перехода статуса дольше порога», «есть producer-спан, но нет
     парного consumer-спана» (потерянное сообщение), «время в статусе > SLA-порога».
   - Alertmanager: маршрутизация/дедуп/эскалация алертов (из Задания 2).
   - On-call / Notifications: алерт в Slack/Telegram, для critical — «звонилка».
     Дежурный по ссылке из алерта проваливается в конкретный трейс в Jaeger.
  Пороговые правила (примеры):
   - заказ в одном статусе дольше ожидаемого для этапа (напр. SUBMITTED без
     PRICE_CALCULATED > 30 мин) → warning;
   - producer-спан publish в RabbitMQ без парного consumer-спана за N мин →
     critical (потерянное сообщение = потерянный заказ);
   - суммарное время заказа приближается к SLA 3 недели → эскалация продавцу.
  Файл (обновлённая схема с алертингом): Task3/jewerly_c4_tracing_alerting.drawio
  На ней к красным компонентам трейсинга добавлены зелёные: Span Metrics,
  Order Journey Monitor, Alertmanager, On-call/Notifications и связи между ними.

======================================================================
5. КОМПРОМИССЫ
======================================================================
Где трейсинг не поможет, пока невозможен или дорог:

  - Разрыв контекста на «чужих» границах. Если внешний партнёр или транспортная
    компания не присылают traceparent, трейс начинается только у нас — путь до/от
    внешней стороны не виден. Полностью не решается на нашей стороне.
  - Проприетарные/legacy-участки. Если какой-то модуль (или сторонняя библиотека
    расчёта) не отдаёт спаны в OTLP, его придётся оборачивать вручную — это
    дорого; иногда экономичнее ограничиться метриками/логами на этом участке.
  - Стоимость хранения при 100% сэмплировании. Полный трейсинг всего трафика —
    дорого по хранилищу и сети. Поэтому tail-based sampling: платим за проблемные
    трейсы, а не за все. Компромисс: часть «нормальных» трейсов не сохраняется.
  - Оверхед инструментирования. Небольшой (обычно единицы %), но на CPU-heavy
    расчёте цены нужно следить, чтобы спаны не добавляли заметной задержки.
  - Ретроспектива. Трейсинг работает «вперёд»: заказы, зависшие ДО внедрения,
    в трейсах не появятся — их разбираем по существующим данным вручную.
  - Не замена метрик/логов. Трейсинг отвечает «где и почему по конкретному
    заказу», но для агрегатов нужны метрики (Задание 2), для деталей — логи
    (Задание 4). Это дополняющие инструменты, а не один вместо другого.

======================================================================
6. БЕЗОПАСНОСТЬ
======================================================================
Трейсы содержат чувствительную информацию о работе бизнеса (пути заказов,
идентификаторы, тайминги), поэтому доступ и данные должны быть защищены.

  Доступ (внутри компании):
   - Аутентификация в Jaeger/Grafana UI: только сотрудники с актуальной учётной
     записью (интеграция с корпоративным SSO/OIDC компании).
   - Авторизация по ролям (RBAC): доступ к трейсам — роли «Поддержка»,
     «Инженер», «Тимлид». Обычные продавцы/операторы UI трейсинга не имеют.
   - Аудит доступа: логировать, кто и какие трейсы смотрел.

  Доступ (снаружи):
   - Система трейсинга НЕ публикуется в интернет. Только внутренняя сеть/VPN;
     доступ через корпоративный доступ (bastion/VPN). Публичного endpoint нет.
   - OTLP-приём Collector’а доступен только сервисам во внутренней сети (network
     policy / security group), не наружу.

  Данные и передача:
   - Минимизация PII: в спаны кладём order.id и технические атрибуты, но НЕ
     персональные/платёжные данные и НЕ содержимое файлов (см. раздел 2).
   - Скраббинг на Collector: процессор-фильтр вырезает случайно попавшие
     чувствительные поля (заголовки Authorization, токены) до сохранения.
   - Шифрование: TLS для OTLP (сервис→Collector) и для доступа к UI (HTTPS);
     шифрование хранилища спанов at-rest.
   - Retention: ограниченный срок хранения (7–14 дней) — меньше данных, меньше
     риск утечки, дешевле хранение.
