ЗАДАНИЕ 2. ВЫБОР И НАСТРОЙКА МОНИТОРИНГА В СИСТЕМЕ

Документ описывает, что и как мы будем измерять, и обосновывает это для бизнеса.
Опирается на анализ из Задания 1 (инициатива I-1 «Наблюдаемость»).

======================================================================
1. МОТИВАЦИЯ
======================================================================
Зачем бизнесу мониторинг (простыми словами, без «ресурсов на всякий случай»):

  1) Мы теряем деньги на «тихих» проблемах. Заказы застревают и теряются в
     потоке магазин → MES → CRM, но узнаём мы об этом от клиента через недели,
     уже потеряв контракт. Мониторинг превращает это в алерт в момент сбоя, а не
     в жалобу через месяц. Это прямая защита выручки.

  2) Яндекс.Метрика больше не даёт полной картины. Она видит поведение
     пользователей на сайте (B2C), но НЕ видит заказы, пришедшие через API от
     партнёров, обмен через очередь и внутренние операции MES/CRM. Значительная
     часть бизнеса теперь «слепая зона».

  3) Нельзя улучшать то, что не измеряешь. Чтобы приоритизировать инициативы из
     Задания 1 (надёжный поток, масштабирование, ускорение дашборда), нужна
     отправная точка — базовые цифры (baseline): сколько заказов, где узкие места,
     какая латентность, где растёт очередь.

  4) Готовность к росту. Нагрузка растёт линейно (+100 заказов/мес). Мониторинг
     насыщенности (saturation) заранее показывает, когда инстанс/БД/очередь
     упрутся в потолок, — успеваем масштабироваться до аварии, а не после.

  5) Ускорение диагностики (MTTR). При инциденте видно, ГДЕ проблема (какой
     сервис, БД, очередь), а не «всё сломалось, ищем вручную». Меньше простоя.

Что бизнес получает измеримо: снижение потерь заказов, соблюдение SLA (3 недели),
быстрее реакция на сбои, обоснованные решения по масштабированию, меньше
репутационных потерь. Стоимость — умеренная (open-source стек + время команды),
окупается предотвращением потери даже одного крупного контракта.

======================================================================
2. АНАЛИЗ СИСТЕМЫ В КОНТЕКСТЕ МОНИТОРИНГА
======================================================================
Что именно нужно наблюдать (объекты мониторинга по C4):

  Запросные (request-driven) компоненты — обрабатывают входящий трафик:
    - Shop API (Spring Boot)        — заказы B2C.
    - CRM API (Spring Boot)         — работа продавцов.
    - MES API (C#)                  — UI операторов + ПУБЛИЧНЫЙ API партнёров + расчёт цены.
    - Фронтенды (Shop/CRM/MES)      — клиентский опыт (RUM), но упор на бэкенд.

  Ресурсные (resource) компоненты — ограниченные ресурсы:
    - Shop DB, MES DB (PostgreSQL)  — одна нода на чтение/запись (узкое место).
    - RabbitMQ                      — критический канал доставки заказов.
    - 3D files storage (S3)         — хранение/чтение 3D-моделей.
    - Инстансы EC2                  — CPU/RAM/диск/сеть каждого сервиса.

  Бизнес-процесс (сквозной) — жизненный цикл заказа:
    - переходы статусов INITIATED → … → CLOSED через три системы и очередь;
    - соблюдение SLA (3 недели), «зависшие» и потерянные заказы.

Ключевые «болевые точки» из Задания 1, которые мониторинг обязан покрыть:
    - потеря/застревание заказов в очереди (A1–A5);
    - конкуренция публичного API партнёров и внутренних операций на MES API (B3);
    - медленный дашборд MES и нагрузка на единственную БД (B2, C1);
    - отсутствие контроля SLA заказа (A4).

======================================================================
3. ВЫБОР ПОДХОДА К МОНИТОРИНГУ
======================================================================
Для разных частей системы — разные подходы (это нормально и осознанно):

  A) RED (Rate, Errors, Duration) — для СЕРВИСОВ, обрабатывающих запросы:
     Shop API, CRM API, MES API и публичного API партнёров.
     Почему: это сервисы «запрос-ответ», нас интересует нагрузка, доля ошибок и
     время ответа — именно то, что чувствует пользователь.

  B) USE (Utilization, Saturation, Errors) — для РЕСУРСОВ:
     инстансы EC2 (CPU/RAM/диск/сеть), PostgreSQL, RabbitMQ, S3.
     Почему: у ресурсов важны загрузка, насыщение (очередь ожидания) и ошибки —
     USE напрямую показывает приближение к потолку под линейный рост.

  C) Четыре золотых сигнала (Latency, Traffic, Errors, Saturation) — для
     КРИТИЧЕСКОГО СКВОЗНОГО потока (пайплайн заказа + RabbitMQ как шина).
     Почему: у потока заказа есть и запросная природа (latency/traffic/errors),
     и ресурсная (saturation очереди и потребителя) — золотые сигналы объединяют
     обе стороны и хорошо ложатся на SLA.

  Дополнительно: слой БИЗНЕС-метрик (заказы по статусам, время в статусе, доля
  просроченных) — поверх технических подходов, отвечает на вопрос «а бизнесу-то
  хорошо?».

Инструментарий (обоснование — в разделе 5): Prometheus (сбор метрик, TSDB) +
Grafana (дашборды) + Alertmanager (алерты) + экспортёры (node/postgres/rabbitmq)
и приложенческие метрики (Micrometer для Spring, prometheus-net для C#).

======================================================================
4. МЕТРИКИ: ЧТО ОТСЛЕЖИВАЕМ, ЗАЧЕМ И КАКИЕ ЯРЛЫКИ
======================================================================
Формат: Метрика — зачем — ярлыки (labels).
Ярлыки нужны, чтобы «разрезать» метрику по сервисам/эндпоинтам/статусам и не
хранить тысячи отдельных метрик. Держим кардинальность под контролем (НЕ кладём
в ярлыки orderId, userId и прочие высококардинальные значения).

--- 4.1. СЕРВИСЫ (подход RED): Shop API, CRM API, MES API ---

  request_rate (RPS), счётчик http_requests_total
    Зачем: базовая нагрузка, тренд роста, всплески (например, после открытия API).
    Ярлыки: service, endpoint (route-шаблон, не raw URL), method, api_type
            (internal|partner — критично, чтобы отделить партнёрский трафик MES
            от операторского), env.

  error_rate — доля ответов 5xx/4xx
    Зачем: качество сервиса; рост 5xx = деградация, рост 429 = упор в лимиты.
    Ярлыки: service, endpoint, method, status_code (или status_class 2xx/4xx/5xx),
            api_type, env.

  request_duration (латентность), гистограмма
    Зачем: скорость ответа, считаем перцентили p50/p95/p99 (не среднее!).
            Прямо ловит «медленный дашборд MES» и деградацию под нагрузкой.
    Ярлыки: service, endpoint, method, env. (гистограмма с бакетами)

  in_flight_requests — число одновременно обрабатываемых запросов
    Зачем: индикатор насыщения пула обработки; рост при исчерпании потоков.
    Ярлыки: service, env.

--- 4.2. БД PostgreSQL (Shop DB, MES DB) — подход USE ---

  db_connections_active / max (utilization пула)
    Зачем: единственная нода на чтение/запись — пул соединений быстро станет
           узким местом; показывает необходимость реплик/пула.
    Ярлыки: db (shop|mes), instance, state (active|idle).

  db_query_duration / slow_queries
    Зачем: находит тяжёлые запросы дашборда MES (C1), обосновывает индексы/кеш.
    Ярлыки: db, query_type (read|write) — без текста запроса.

  db_replication_lag (после ввода реплик)
    Зачем: контроль отставания реплик чтения, чтобы дашборд не показывал старое.
    Ярлыки: db, replica.

  db_locks / deadlocks, transactions_rate
    Зачем: конкуренция при назначении заказа оператору («кто первый взял», C2).
    Ярлыки: db.

  db_disk_usage, cache_hit_ratio
    Зачем: насыщение диска (saturation) и эффективность shared_buffers.
    Ярлыки: db, instance.

--- 4.3. RabbitMQ — четыре золотых сигнала (это шина заказов, критично) ---

  queue_depth / messages_ready — глубина очереди (НЕПРОЧИТАННЫЕ сообщения)
    Зачем: ГЛАВНАЯ метрика надёжности заказов. Рост = потребитель не справляется
           или упал → заказы застревают (корень боли из Задания 1).
    Ярлыки: queue, topic, env.

  consumer_lag / messages_unacked
    Зачем: отставание потребителя; растущий unacked = обработка виснет.
    Ярлыки: queue, consumer, env.

  publish_rate / deliver_rate / ack_rate
    Зачем: traffic шины; расхождение publish и ack = теряем/копим сообщения.
    Ярлыки: queue, topic.

  dead_letter_count (после внедрения DLQ, I-2)
    Зачем: сообщения, которые не удалось обработать — прямой сигнал о потерянных
           заказах, требующих ручного разбора.
    Ярлыки: queue.

  rabbitmq_node_saturation (память/диск alarm, файловые дескрипторы, соединения)
    Зачем: RabbitMQ при переполнении памяти блокирует publishers → стоп приёма.
    Ярлыки: node.

--- 4.4. ИНФРАСТРУКТУРА (EC2-инстансы) — подход USE ---

  cpu_utilization
    Зачем: базовое насыщение; расчёт цены на MES API — CPU-затратный.
    Ярлыки: instance, service, env.

  memory_usage
    Зачем: утечки, OOM-kill; предвестник рестартов.
    Ярлыки: instance, service, env.

  disk_usage / disk_io
    Зачем: переполнение диска (логи, S3-кеш, БД) кладёт сервис; IO — узкое место БД.
    Ярлыки: instance, service, mountpoint.

  network_io
    Зачем: насыщение сети, аномальный трафик (например, выгрузка 3D-файлов).
    Ярлыки: instance, service, direction (in|out).

--- 4.5. ДОСТУПНОСТЬ ---

  service_up (health-check, проба /health)
    Зачем: жив ли сервис вообще; основа для алерта на падение и расчёта аптайма.
    Ярлыки: service, instance, env.

--- 4.6. БИЗНЕС-МЕТРИКИ (поверх подходов; закрывают A3, A4) ---

  orders_total — счётчик созданных заказов
    Зачем: реальный объём бизнеса, включая API-заказы (то, что Метрика не видит).
    Ярлыки: channel (b2c|partner), env. (partner можно детализировать по partner_id,
            если их немного — иначе выносим в логи).

  orders_by_status — текущее число заказов в каждом статусе (gauge)
    Зачем: видно «пробки» в пайплайне — где заказы копятся, там узкое место.
    Ярлыки: status (INITIATED…CLOSED), channel.

  order_time_in_status — время нахождения в статусе (гистограмма)
    Зачем: находим этап, на котором заказы «висят»; основа контроля SLA.
    Ярлыки: status, channel.

  orders_overdue — число заказов, превысивших SLA (3 недели) (gauge)
    Зачем: ПРЯМАЯ бизнес-боль. Алерт на рост = теряем клиента прямо сейчас.
    Ярлыки: channel, current_status.

  order_conversion — переходы SUBMITTED → CLOSED (воронка)
    Зачем: сквозная «доходимость» заказа; падение = где-то теряем.
    Ярлыки: channel.

5. ПЛАН ДЕЙСТВИЙ (черновик ТЗ)
======================================================================
Э т а п  1. Инфраструктура мониторинга
  1.1. Развернуть Prometheus (сбор + TSDB) как отдельный инстанс; настроить
       retention (напр. 15–30 дней «горячих» данных) и, при необходимости, remote-
       storage/Thanos для долгого хранения. Обосновать выбор: pull-модель, зрелые
       экспортёры, интеграция с Grafana/Alertmanager.
  1.2. Развернуть Grafana (дашборды) и Alertmanager (маршрутизация алертов).
  1.3. Задать соглашение об именовании метрик и ярлыков; зафиксировать правила
       кардинальности (запрет orderId/userId в ярлыках).

Э т а п  2. Сбор технических метрик
  2.1. node_exporter на каждый EC2-инстанс (CPU/RAM/диск/сеть — USE).
  2.2. postgres_exporter для Shop DB и MES DB.
  2.3. Включить встроенный prometheus-плагин RabbitMQ (queue depth, lag, DLQ).
  2.4. Инструментировать сервисы приложенческими метриками (RED):
       Spring (Shop/CRM API) — Micrometer + эндпоинт /actuator/prometheus;
       MES API (C#) — prometheus-net, эндпоинт /metrics.
  2.5. Health-проба /health на каждом сервисе + blackbox-мониторинг снаружи.

Э т а п  3. Бизнес-метрики жизненного цикла заказа
  3.1. Инструментировать смену статусов заказа (во всех трёх системах) метриками
       orders_by_status / order_time_in_status / orders_overdue.
  3.2. Отдельно пометить канал заказа (b2c|partner), чтобы закрыть «слепую зону»
       API-заказов относительно Яндекс.Метрики.

Э т а п  4. Дашборды в Grafana
  4.1. Обзорный дашборд системы (RED по сервисам, USE по ресурсам).
  4.2. Дашборд надёжности заказов (RabbitMQ: depth/lag/DLQ + золотые сигналы).
  4.3. Бизнес-дашборд заказов (по статусам, SLA, воронка, каналы).
  4.4. Дашборд БД (соединения, slow queries, locks, диск) — под ускорение
       дашборда MES (связка с Заданием 5, кеширование).

Э т а п  5. Алертинг (Alertmanager)
  5.1. Правила алертов (см. раздел 6: пороги насыщенности).
  5.2. Маршрутизация: Slack/Telegram для team, PagerDuty/«звонилка» для critical.
  5.3. Дежурства (on-call), severity-уровни (warning|critical), группировка и
       подавление шума (inhibition).

Э т а п  6. Закрепление
  6.1. Runbook’и на ключевые алерты (что делать при росте queue depth и т.п.).
  6.2. Зафиксировать baseline-цифры как отправную точку для инициатив Задания 1.
  6.3. Обзор SLO/SLI на основе собранных метрик (следующий шаг зрелости).

======================================================================
6. ДОПОЛНИТЕЛЬНО: ПОКАЗАТЕЛИ НАСЫЩЕННОСТИ (SATURATION) И РЕАКЦИЯ
======================================================================
Насыщенность — «сколько ещё запаса до потолка». Пороги двухуровневые:
WARNING (готовимся действовать) и CRITICAL (действуем немедленно). Значения —
стартовые, калибруются по собранному baseline.

  Ресурс/метрика            WARNING      CRITICAL     Почему такой порог
  ------------------------------------------------------------------------------
  CPU инстанса              > 70% (5м)   > 90% (5м)   Запас на пики; расчёт цены
                                                      на MES API — CPU-heavy.
  Память инстанса           > 75%        > 90%        Риск OOM/рестарта до 100%.
  Диск                      > 75%        > 90%        Заполнение диска = отказ;
                                                      нужен запас на реакцию.
  Пул соединений БД         > 70%        > 90%        Единственная нода — упор в
                                                      соединения кладёт запись.
  RabbitMQ queue depth      > N (тренд)  растёт 10м   Копление = заказы застревают;
                                        не убывая     порог N по baseline канала.
  Consumer lag / unacked    > 1–2 мин    > 5–10 мин   Обработка виснет → SLA под
                                                      угрозой.
  DLQ (dead letters)        > 0          рост         Любое письмо в DLQ = потен-
                                                      циально потерянный заказ.
  p99 латентность сервиса   > 2× baseline > SLA-порог Деградация польз. опыта.
  error_rate (5xx)          > 1%         > 5%         Заметная деградация сервиса.
  orders_overdue (SLA 3нед) > 0          рост         Прямая потеря клиента.

Что происходит при превышении (эскалация по severity):

  WARNING (превентивно, рабочее время):
    - алерт в командный канал (Slack/Telegram);
    - автоматически заводится тикет на разбор/тюнинг (индексы, тюнинг пула, план
      масштабирования);
    - для ресурсов с автоскейлингом (цель Задания 1) — авто-добавление инстанса.

  CRITICAL (немедленно, круглосуточно):
    - алерт дежурному через PagerDuty + автоматическая «звонилка» (phone/SMS);
    - авто-действия где безопасно: горизонтальное масштабирование (доп. инстанс/
      потребитель очереди), throttling/rate-limit партнёрского API, чтобы
      защитить внутренние операции (проблема B3);
    - открытие инцидента, запуск runbook, уведомление продакт-менеджера при
      влиянии на заказы/SLA.

  Специальные реакции:
    - queue depth / DLQ растёт → автоматически поднять доп. потребителя, письмо
      в саппорт по «зависшим» заказам, ручной разбор DLQ по runbook.
    - orders_overdue растёт → уведомление продавцу/администратору для ручной
      эскалации конкретных заказов (не ждём жалобы клиента).
    - партнёрский API упирается в лимиты (429 растёт) → уведомить партнёра,
      пересмотреть квоты, ускорить вынос публичного API в отдельный сервис (I-4).

Принцип: алерты должны быть actionable (на каждый — понятное действие/runbook),
иначе они превращаются в шум и их перестают читать.
