ЗАДАНИЕ 4. АРХИТЕКТУРНОЕ РЕШЕНИЕ ПО ЛОГИРОВАНИЮ

Цель: системно упростить разбор проблем внутри сервисов и снизить нагрузку на
поддержку — вместо разбора «со слов клиента» иметь факты в логах.
Опирается на Задание 1 (I-1) и дополняет мониторинг (Задание 2) и трейсинг
(Задание 3): метрики говорят «что», трейсинг — «где», логи — «что именно
произошло в деталях».

======================================================================
1. АНАЛИЗ СИСТЕМЫ В КОНТЕКСТЕ ЛОГИРОВАНИЯ
======================================================================
Откуда собираем логи (отмечено на схеме, файл в разделе 4):
  - Shop API, CRM API, MES API — бэкенды: бизнес-события и ошибки (главное);
  - Internet Shop / CRM / MES (фронты) — клиентские ошибки (JS), но приоритет
    ниже, чем бэкенды;
  - RabbitMQ — publish/consume/ack/reject, попадание в DLQ (границы, где теряются
    заказы);
  - Shop DB, MES DB (PostgreSQL) — slow-query log, ошибки, deadlock’и;
  - публичный API MES — отдельно, т.к. это внешний трафик партнёров (безопасность).

Сквозная корреляция — обязательное условие. В каждой записи лога должны быть
correlation_id и order_id, единые для всех сервисов на пути одного заказа
(correlation_id = trace_id из Задания 3). Без этого логи трёх систем не связать.

1.1. НЕОБХОДИМЫЕ ЛОГИ УРОВНЯ INFO (бизнес- и ключевые технические события)
Формат — структурированный (JSON). Общие поля каждой записи:
  timestamp, level, service, env, host, correlation_id (=trace_id), order_id,
  message, event.

  Жизненный цикл заказа (главное — по этим логам восстанавливаем судьбу заказа):
   1) order.status_changed — смена статуса: order_id, old_status, new_status,
      actor (customer|seller|operator|api_partner|system), channel (b2c|partner),
      timestamp. (пример из задания: изменение статуса заказа)
   2) order.created — order_id, channel, customer_id (идентификатор, не ФИО),
      source (shop|partner_api).
   3) order.file_uploaded — order_id, file_id, size (без содержимого файла).
   4) order.price_calculated — order_id, price, calc_duration_ms.
   5) order.manufacturing_approved / started / completed — order_id, operator_id.
   6) order.shipped / closed — order_id, close_reason (carrier_msg|manual).

  Интеграции и границы (где заказы теряются):
   7) mq.published — queue/topic, message_id, order_id (producer-сторона).
   8) mq.consumed — queue, message_id, order_id, consumer, result (ok|retry|dlq).
   9) api.request (публичный API партнёров) — endpoint, method, status_code,
      partner_id, duration_ms (аудит внешнего доступа).
   10) auth.login — user_id, role, result (нужно для аудита и безопасности).

  Технические INFO:
   11) service.startup/shutdown — version, env (сопоставление с релизом).
   12) job.completed — плановые задачи (напр. пересчёт дашборда).

1.2. ДРУГИЕ УРОВНИ ЛОГИРОВАНИЯ (когда применяем)
  - ERROR — операция не выполнена и требует внимания: исключение при обработке
    заказа, ошибка записи в БД, сообщение ушло в DLQ, ошибка вызова S3. Пишем
    стек и контекст (order_id, correlation_id). ERROR — кандидаты на алерт.
  - WARN — операция выполнена, но с отклонением/риском: ретрай сообщения,
    приближение к rate-limit партнёра, деградация (медленный запрос > порога),
    использование фолбэка. Ещё не инцидент, но сигнал.
  - DEBUG — подробности для отладки (значения переменных, промежуточные шаги).
    Включаем ТОЧЕЧНО и временно (по сервису/по фиче), НЕ на постоянку в prod —
    иначе объём и стоимость взрываются. Управляем уровнем без передеплоя (динам.
    конфиг лог-уровня).
  - TRACE — максимально подробно; только локально/в dev, в prod практически нет.
  - FATAL/CRITICAL — сервис не может продолжать работу (падение при старте,
    потеря соединения с критичным ресурсом) — немедленный алерт.
  По умолчанию в prod: INFO (+ WARN/ERROR). DEBUG — по требованию.

2. МОТИВАЦИЯ
======================================================================
Почему логирование и что даёт компании:
  - Сейчас проблему разбирают «со слов клиента», разработчик тратит часы на
    ручной поиск по трём системам. Централизованные структурированные логи с
    correlation_id/order_id дают ответ «что именно случилось с заказом N» за
    минуты — без обращения к клиенту.
  - Снижают нагрузку на поддержку: типовые вопросы закрываются по логам без
    эскалации на разработчиков.
  - Дают доказательную базу: не «кажется, потерялось», а конкретная запись
    (ушло в DLQ / не дошло / упало с такой-то ошибкой).
  - Превращаются в систему анализа: алерты на всплеск ERROR и аномалии (DDoS,
    см. раздел 4) — реакция до жалоб.

Метрики решения, на которые влияет логирование:
  Технические:
   1) MTTR (время разбора инцидента) — снижается кратно (поиск по логам вместо
      ручной корреляции).
   2) Доля инцидентов, воспроизводимых/объяснённых по логам без запроса клиенту —
      растёт (target > 80%).
   3) Время обнаружения сбоя (MTTD) — снижается за счёт алертов на ERROR/аномалии.
  Бизнесовые:
   4) Нагрузка на поддержку — среднее время обработки обращения и доля обращений,
      эскалированных в разработку, — снижаются.
   5) Количество «потерянных» заказов, обнаруженных ПРОАКТИВНО (по логам DLQ), а
      не по звонку клиента — растёт → меньше потерянных контрактов.

======================================================================
3. ПРИОРИТИЗАЦИЯ: ЛОГИ И ТРЕЙСИНГ — ЧТО ПЕРВЫМ И ПОЧЕМУ
======================================================================
Всё сразу команда не потянет. Приоритет — по «пути денег» и месту потери заказов.

  Очередь приоритета (и логи, и трейсинг — вместе, т.к. correlation_id общий):
   1) MES API + RabbitMQ (границы очереди). ЗДЕСЬ теряются заказы (создание в
      CRM через сообщение из очереди от MES, расчёт цены). Максимальная отдача:
      закрываем корневую боль из Задания 1. Плюс это внешний публичный API —
      важен аудит.
   2) CRM API. Вторая критичная граница (заказ «зависает» перед
      MANUFACTURING_APPROVED / CLOSED). Продавцы теряют заказы здесь.
   3) Shop API. Начало пути (INITIATED…SUBMITTED, загрузка 3D). Важно, но реже
      является местом «пропажи», чем границы очереди.
   4) Фронтенды (Shop/CRM/MES) и БД slow-log. Дают контекст, но не корневые для
      потери заказов — последними.

  Почему так: сначала инструментируем участки, где заказы реально теряются и где
  сходится внешний трафик (MES API + очередь), затем расширяемся к краям. Это
  даёт наибольшее снижение потерь и нагрузки на поддержку на единицу усилий.

4. ПРЕДЛАГАЕМОЕ РЕШЕНИЕ
======================================================================
4.1. Технологии и компоненты
  Стек (обоснование выбора — в разделе 5, доп. задание): OpenSearch + OpenSearch
  Dashboards + агент Fluent Bit/Vector + пайплайн Logstash/Vector.

  Новые компоненты (на схеме — ОРАНЖЕВЫМ):
   - Log Agent (Fluent Bit/Vector) — на каждом хосте: сбор stdout/файловых логов,
     парсинг JSON, добавление метаданных.
   - Log Pipeline (Logstash/Vector) — централизованная обработка, обогащение,
     МАСКИРОВАНИЕ чувствительных полей, маршрутизация по индексам.
   - Log Storage / Search (OpenSearch) — хранение и полнотекстовый поиск,
     отдельные индексы по сервисам, ILM-политики retention.
   - Log Dashboards (OpenSearch Dashboards) — поиск/разбор по order_id.
   - Log Alerting / Anomaly (OpenSearch Alerting) — правила и детекция аномалий.
   - Роль Support/Engineer — работает с логами.

  Доработки существующих компонентов:
   - Shop/CRM API (Spring): перейти на структурированное JSON-логирование
     (Logback + logstash-encoder), прокидывать correlation_id/order_id через MDC.
   - MES API (C#): Serilog с JSON-выводом, тот же correlation_id (из trace_id).
   - Проброс correlation_id из HTTP-заголовков и из заголовков сообщений RabbitMQ
     (единый id с трейсингом из Задания 3).
   - Внедрить общий стандарт полей лога (log schema) для всех сервисов.

  Файл со схемой: Task4/jewerly_c4_logging.drawio
  На схеме отражены новые компоненты и связи «логи → агент → пайплайн →
  OpenSearch → Dashboards», а также алертинг/аномалии и роль инженера.

4.2. БЕЗОПАСНОСТЬ И РАБОТА С ЧУВСТВИТЕЛЬНЫМИ ДАННЫМИ
  - Что НЕ логируем: пароли, токены, платёжные данные, содержимое 3D-файлов,
    полные тела запросов. Персональные данные (ФИО, адрес, контакты) — не в
    открытом виде.
  - Маскирование/обфускация на этапе Log Pipeline: PII вырезается/хэшируется до
    индексации (order_id и customer_id — можно, ФИО/адрес — нет). Это защита,
    даже если разработчик случайно залогировал лишнее.
  - Доступ (RBAC, интеграция с корпоративным SSO):
      * роль «Поддержка» — поиск по логам приложений (без индексов безопасности/
        аудита с чувствительными полями);
      * роль «Инженер/Разработчик» — полный доступ к логам приложений;
      * роль «Безопасность/Аудит» — доступ к auth/api-audit индексам;
      * продавцы/операторы доступа к системе логов не имеют.
  - Изоляция: система логов только во внутренней сети/через VPN, наружу не
    публикуется. TLS в передаче (агент→пайплайн→хранилище) и HTTPS к Dashboards.
  - Аудит доступа к самим логам (кто что искал), особенно к чувствительным индексам.

4.3. ПОЛИТИКА ХРАНЕНИЯ (RETENTION)
  - Отдельные индексы под каждый сервис/тип: logs-shop-api-*, logs-crm-api-*,
    logs-mes-api-*, logs-rabbitmq-*, logs-audit-*. Разделение упрощает доступы,
    retention и ускоряет поиск.
  - Срок хранения (управляется ILM/ISM, «горячий→тёплый→холодный→удаление»):
      * app-логи (INFO/WARN/ERROR): 14–30 дней «горячих», затем архив/удаление;
      * audit/security (auth.login, api.request партнёров): дольше, 90–180 дней
        (требования аудита/расследований);
      * DEBUG (если временно включали): 3–7 дней.
  - Оценка объёма (грубо, для sizing кластера): при линейном росте заказов
    прикидываем средний размер записи (~1–2 КБ) × число событий/заказ × число
    заказов/день. Пример: 5 000 заказов/день × ~20 событий × 1.5 КБ ≈ 150 МБ/день
    app-логов + пики ошибок. Индекс и репликация ×(1.5–2). Цифры калибруем по
    реальному baseline из Задания 2 и закладываем rollover по размеру индекса.
  - Компрессия и уменьшение репликации на «тёплых» данных для экономии.

4.4. ОТ СБОРА ЛОГОВ — К АНАЛИЗУ ЛОГОВ (алертинг и аномалии)
  Алертинг (на базе OpenSearch Alerting, единые каналы с Заданием 2):
   - всплеск ERROR по сервису > порога за интервал → alert;
   - появление записей result=dlq (сообщение в DLQ) → critical: потенциально
     потерянный заказ, требует ручного разбора;
   - рост 5xx/429 на публичном API партнёров → alert (деградация/лимиты);
   - отсутствие ожидаемого события (например, за N времени нет order.consumed на
     опубликованный order.published) → застрявший заказ.
  Поиск аномалий:
   - Резкие всплески частоты событий. Пример из задания: было ~4 записи
     order.created/сек, стало 10 000/сек → вероятная DDoS-атака/скрейпинг через
     публичный API. Реакция: алерт безопасности, включение rate-limit/защиты,
     уведомление on-call.
   - Аномалии применяем к: числу заказов по каналам, частоте ошибок, частоте
     auth.login по одному user_id/ip (перебор), объёму трафика партнёра.
   - Технически — Anomaly Detection в OpenSearch (или простые пороги/скользящие
     окна на старте, ML-детекторы — позже).
  Действия по алертам — по модели эскалации из Задания 2 (Slack/Telegram →
  «звонилка» для critical), с ссылкой из алерта в конкретный запрос логов.

Плюсы/минусы кратко:
  - ELK: + зрелость, богатый поиск и Kibana; − смена лицензии (не Apache),
    часть фич за деньги, дорогое хранение.
  - OpenSearch: + Apache 2.0 (нет лицензионных рисков), полная функциональность
    без платной подписки, совместим с экосистемой ES; − эксплуатация кластера
    нетривиальна, ресурсоёмкость как у ES.
  - Splunk: + мощнейшая аналитика (SPL), enterprise-поддержка, минимум ops;
    − очень дорогой при росте объёма (а он у нас линейный), vendor lock-in.
  - Loki: + дёшево хранить, просто, отличная связка с Grafana (уже есть по
    Заданию 2); − слабый full-text поиск (индексирует метки, не содержимое) —
    для детального разбора «что случилось с заказом» этого может не хватить.

ВЫБОР: OpenSearch.
Обоснование: нужен сильный полнотекстовый поиск и аналитика по order_id/
correlation_id (это ядро задачи — «что случилось с заказом»), при этом важны
контролируемая стоимость и отсутствие лицензионных/vendor-рисков при линейном
росте объёма. OpenSearch даёт функциональность ELK под Apache 2.0 без платных
подписок и лок-ина, имеет встроенные Alerting и Anomaly Detection (нужны в
разделе 4). Splunk отпадает по стоимости при росте, Loki — по слабому full-text
поиску, «чистый» Elastic — по лицензии и платным фичам.
Оговорка: метрики/дашборды остаются в Grafana (Задание 2); при желании Grafana
подключается и к OpenSearch как data source — единый UI наблюдаемости.
