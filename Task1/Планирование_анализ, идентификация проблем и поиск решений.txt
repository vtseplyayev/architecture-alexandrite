ЗАДАНИЕ 1. ПЛАНИРОВАНИЕ: АНАЛИЗ, ИДЕНТИФИКАЦИЯ ПРОБЛЕМ И ПОИСК РЕШЕНИЙ
Компания «Александрит». Архитектор: В. Цепляев.

======================================================================
0. КРАТКОЕ РЕЗЮМЕ
======================================================================
Бизнес теряет заказы и контракты не из-за производства (оно тянет 2х рост),
а из-за IT-системы. Три корневые причины и три инициативы под них на полгода
(подробное обоснование выбора — в разделе 5.2):

  1) Заказы теряются и застревают в асинхронном потоке магазин → MES → CRM
     (RabbitMQ без гарантированной доставки, без контроля статуса и SLA).
     → I-2. Надёжный асинхронный поток заказов.
  2) Нет наблюдаемости — реагируем по жалобам, а не по алертам.
     → I-1. Наблюдаемость + мониторинг жизненного цикла и SLA заказа.
  3) Система не масштабируется под линейный рост: по одному инстансу на сервис,
     одна БД на чтение/запись, публичный API на том же инстансе MES.
     → I-3. Масштабирование сервисов и БД + ускорение дашборда MES.

======================================================================
1. КЛЮЧЕВЫЕ НАБЛЮДЕНИЯ ПО СХЕМЕ C4 (источники проблем)
======================================================================
Состав системы (кратко): B2C-магазин (Vue + Shop API/Spring + Shop DB), CRM
(Vue + CRM API/Spring), MES (React + MES API/C# + MES DB), S3 для 3D-файлов,
RabbitMQ для обмена. Инфраструктура — dev/release/prod в Yandex Cloud: по одному
инстансу на сервис, managed-БД с единственным инстансом на чтение и запись, HA
нет. CI/CD: dev автоматически, release и prod — вручную. QA — один ручной E2E,
баги high/highest блокируют прод.

Что важно заметить именно на схеме (не следует из текста кейса):
  * CRM API пишет НАПРЯМУЮ в Shop DB — общая БД у двух систем (сильная связность).
  * Внешний «API user» ходит НАПРЯМУЮ в MES API — тот же инстанс, что обслуживает
    UI операторов и считает цену. Нет отдельного шлюза/сервиса для партнёров.
  * Статус заказа меняют три разные системы (магазин: INITIATED, FILE_UPLOADED,
    SUBMITTED; MES: PRICE_CALCULATED, MANUFACTURING_STARTED/COMPLETED, PACKAGING,
    SHIPPED; CRM: MANUFACTURING_APPROVED, CLOSED), данные размазаны по трём БД —
    распределённая сага без оркестратора и без единого источника правды.

======================================================================
2. ИДЕНТИФИКАЦИЯ ПРОБЛЕМ (существующие и потенциальные)
======================================================================
Сгруппировано по областям. В скобках — связь с симптомами из описания.

A. НАДЁЖНОСТЬ ПОТОКА ЗАКАЗОВ / ПОТЕРЯ ЗАКАЗОВ  (главная боль бизнеса)
  A1. Асинхронный обмен через RabbitMQ без гарантий доставки: нет подтверждений
      (ack), нет persistent-очередей, нет DLQ, нет ретраев, нет идемпотентности
      у потребителей. Сообщение о создании/смене статуса заказа может потеряться
      или обработаться дважды → «заказ пропал» (жалобы B2C и API-пользователей).
  A2. Нет паттерна transactional outbox/inbox: запись в БД и публикация в очередь
      не атомарны. Падение между «сохранили» и «опубликовали» = молчаливая потеря.
  A3. Нет единого источника правды по статусу заказа и нет оркестрации саги.
      Заказ может «застрять» между системами (например, PRICE_CALCULATED есть в
      MES, но сообщение в CRM не дошло — MANUFACTURING_APPROVED никогда не наступит).
  A4. Нет контроля SLA заказа (обещано 3 недели). Никто не отслеживает
      «просроченные»/«зависшие» заказы автоматически → узнаём от клиента через месяцы.
  A5. Один инстанс-потребитель очереди — единая точка отказа; при его падении
      или отставании заказы копятся/теряются.

B. МАСШТАБИРУЕМОСТЬ И ДОСТУПНОСТЬ
  B1. По одному инстансу на каждый сервис. Нельзя масштабироваться горизонтально
      под линейный рост (+100 заказов/мес) и всплеск после открытия API.
  B2. Одна БД-инстанс на чтение и запись у каждого сервиса. Нет read-реплик.
      Тяжёлые чтения (дашборд) конкурируют с записью.
  B3. MES API совмещает три роли: бэкенд UI операторов, публичный API партнёров и
      расчёт цены (CPU-затратно). Партнёрский трафик и расчёт «съедают» ресурс,
      от которого зависит работа операторов.
  B4. Единые точки отказа: один RabbitMQ, одна БД, один инстанс каждого сервиса.
      Нет HA/резервирования.

C. ПРОИЗВОДИТЕЛЬНОСТЬ ДАШБОРДА MES
  C1. Первая страница MES (список заказов по статусам) грузится долго даже после
      фильтра и пагинации. Вероятные причины: чтение из основной БД под нагрузкой
      записи; offset-пагинация на больших смещениях; отсутствие нужных индексов
      (status, created_at); отсутствие модели чтения/кеша; возможные N+1.
  C2. Операторам нужны самые новые заказы первыми (от этого зависит оплата), а
      значит нужны сортировка по времени с индексом, keyset/cursor-пагинация и
      «горячий» кеш. Конкуренция за «кто первый взял» = блокировки при назначении.

D. АРХИТЕКТУРА ДАННЫХ И СВЯЗНОСТЬ
  D1. Общая Shop DB для Shop API и CRM API — нарушение владения данными,
      связность релизов, взаимные блокировки, риск рассинхронизации.
  D2. Дублирование данных заказа в трёх БД без чёткого владельца поля «статус»
      → рассинхронизация, потерянные обновления (lost update).

E. НАБЛЮДАЕМОСТЬ (это темы заданий 2–5 спринта)
  E1. Нет мониторинга инфраструктуры и приложений, нет дашбордов, нет алертов.
  E2. Нет распределённого трейсинга — невозможно проследить путь заказа через
      магазин → очередь → MES → CRM и найти, где он «умер».
  E3. Нет централизованного структурированного логирования и корреляции по
      orderId/traceId.
  E4. Нет бизнес-метрик (кол-во заказов по статусам, время в статусе, доля
      просроченных, глубина очереди, lag потребителя).

F. ПРОЦЕСС ПОСТАВКИ И КАЧЕСТВО
  F1. Ручной E2E одним QA — узкое место; время растёт вместе с объёмом функций,
      релиз задерживается (раньше до месяца, сейчас больше).
  F2. Баги high/highest блокируют прод при отсутствии автотестов и быстрой
      обратной связи.
  F3. Ручной деплой в release и prod; нет канареечных выкаток, фиче-флагов,
      быстрого отката. Риск инцидентов и медленная доставка фиксов.

G. БЕЗОПАСНОСТЬ И УПРАВЛЕНИЕ ПУБЛИЧНЫМ API
  G1. Публичный API = внутренний MES API. Нет API-gateway, rate limiting,
      квот, версионирования, отдельного SLA и изоляции от внутренней нагрузки.
  G2. Риск: злоупотребление/пики со стороны партнёров кладут внутренние операции.

======================================================================
3. ИНИЦИАТИВЫ (что делаем, чтобы устранить проблемы)
======================================================================
Каждая инициатива помечена проблемами, которые закрывает.

  I-1. Наблюдаемость и контроль жизненного цикла заказа.
       Мониторинг инфраструктуры/приложений, дашборды и алерты (задание 2),
       распределённый трейсинг (задание 3), централизованные структурированные
       логи с корреляцией по orderId/traceId (задание 4). Отдельно — БИЗНЕС-
       мониторинг заказов: метрики по статусам, время в статусе, доля
       просроченных по SLA, глубина очереди и lag потребителя, алерты на
       «зависшие» заказы. Закрывает: E1–E4, A4, частично A3.

  I-2. Надёжный асинхронный поток заказов.
       Persistent-очереди и подтверждения (publisher/consumer ack), transactional
       outbox/inbox, идемпотентные потребители (dedup по messageId/orderId),
       Dead Letter Queue + ретраи с backoff, алерт на рост DLQ. Закрывает: A1, A2, A5.

  I-3. Масштабирование сервисов и БД + ускорение дашборда MES.
       Stateless-сервисы за балансировщиком, автоскейлинг-группы (min>1); read-
       реплики БД и роутинг чтений на них; для дашборда — отдельная модель чтения
       (CQRS/materialized view), кеширование (задание 5), keyset-пагинация и
       индексы (status, created_at). Закрывает: B1, B2, C1, C2, B4 (частично).

  I-4. Разделение публичного API и внутреннего MES.
       Выделить API-gateway для партнёров (аутентификация, rate limiting, квоты,
       версионирование, отдельный SLA) и отдельный масштабируемый сервис приёма
       заказов; вынести расчёт цены в отдельный сервис. Закрывает: B3, G1, G2.

  I-5. Единый источник правды и оркестрация статуса заказа.
       Выделенная ответственность за статус заказа (сервис/агрегат Order с
       явной сагой и переходами статусов), контроль SLA и авто-эскалация
       просрочек. Закрывает: A3, A4, D2.

  I-6. Развязка данных Shop/CRM.
       Убрать прямой доступ CRM API к Shop DB; общение только через API/события,
       чёткое владение данными. Закрывает: D1, D2 (частично).

  I-7. HA инфраструктуры.
       Кластер RabbitMQ, managed БД с репликами/failover, несколько инстансов
       сервисов, health-checks. Закрывает: B4.

  I-8. Автоматизация тестирования.
       Пирамида тестов: юнит + интеграционные + автоматизированные E2E в CI;
       контрактные тесты для очереди и публичного API; QA-инженер строит
       автоматизацию (есть прототипы). Закрывает: F1, F2.

  I-9. Улучшение CI/CD.
       Автодеплой в release/prod, канареечные выкатки, фиче-флаги, быстрый откат.
       Закрывает: F3.

  I-10. Локальные быстрые задачи (low-hanging fruit, делаем попутно):
       - Индексы на MES DB под запросы дашборда (status, created_at).
       - Перевод дашборда на keyset-пагинацию вместо offset.
       - Включить persistent-сообщения и manual ack в RabbitMQ.
       - Базовые health-check и алерт на глубину очереди.
       Это дешёвые изменения с быстрым эффектом ещё до крупных эпиков.

======================================================================
4. ПРИОРИТИЗАЦИЯ (ход рассуждений)
======================================================================
Критерии приоритета: (1) влияние на главную бизнес-боль — потеря заказов и
контрактов; (2) стоимость/скорость реализации; (3) является ли фундаментом для
других инициатив; (4) риск бездействия.

Логика:
  - Сначала нужно ВИДЕТЬ проблему. Нельзя чинить потерю заказов вслепую —
    поэтому наблюдаемость и бизнес-мониторинг SLA (I-1) идут первыми: дёшево,
    быстро, сразу показывают, где именно застревают заказы, и это фундамент для
    всех остальных решений (и для заданий 2–5 спринта).
  - Параллельно бьём в корень потери заказов — надёжный поток (I-2): именно
    негарантированная доставка объясняет «заказ пропал» у B2C и партнёров.
  - Затем снимаем ограничение роста и тормоза дашборда (I-3): линейный рост и
    всплеск после API требуют горизонтального масштаба и реплик; дашборд —
    ежедневная боль операторов и их оплаты.
  - Далее — изоляция публичного API (I-4) и единый статус/сага (I-5): важны,
    но их эффект ограничен, пока не решены I-1..I-3.
  - Развязка данных (I-6), HA (I-7), автотесты (I-8) и CI/CD (I-9) — важные, но
    более долгие/структурные; параллельно тянем быстрые задачи I-10.

Итоговый порядок приоритета:
  1) I-1  Наблюдаемость + мониторинг SLA заказа        [must, фундамент]
  2) I-2  Надёжный асинхронный поток заказов           [must, корень потери]
  3) I-3  Масштабирование + ускорение дашборда MES     [must, рост нагрузки]
  4) I-4  Разделение публичного API и MES              [high]
  5) I-5  Единый источник правды и сага статуса        [high]
  6) I-8  Автоматизация тестирования                   [high, ускоряет релизы]
  7) I-6  Развязка данных Shop/CRM                     [medium]
  8) I-9  Улучшение CI/CD                              [medium]
  9) I-7  HA инфраструктуры                            [medium]
     I-10 Быстрые локальные задачи                     [делаем непрерывно]

5. ОТВЕТЫ НА ВОПРОСЫ ЗАДАНИЯ
======================================================================
5.1. ЦЕЛЕВАЯ АРХИТЕКТУРА ЧЕРЕЗ ПОЛГОДА

Через полгода «Александрит» приходит к наблюдаемой, надёжной и горизонтально
масштабируемой системе:

  - Наблюдаемость как основа: метрики (инфраструктура + приложения + БИЗНЕС-
    метрики заказов), распределённый трейсинг сквозь магазин → очередь → MES →
    CRM, централизованные структурированные логи с корреляцией по orderId/
    traceId. Дашборды и алерты, включая алерт на заказы, нарушившие SLA 3 недели,
    и на рост DLQ/lag потребителя. Инциденты видим по алертам, а не по жалобам.

  - Надёжный поток заказов: persistent-очереди, publisher/consumer ack,
    transactional outbox/inbox, идемпотентные потребители, DLQ + ретраи.
    Ни одно сообщение о заказе не теряется молча; проблемные уходят в DLQ и
    разбираются.

  - Единый статус заказа: явный владелец статуса и сага переходов, контроль SLA
    и авто-эскалация просрочек продавцу/администратору.

  - Масштабируемость: stateless-сервисы за балансировщиком в автоскейлинг-
    группах (min > 1 инстанса); БД с read-репликами, чтения роутятся на реплики;
    RabbitMQ в кластере. Никаких единичных точек отказа на критическом пути.

  - Быстрый дашборд MES: отдельная модель чтения (CQRS/materialized view),
    кеширование «горячих» новых заказов, keyset-пагинация, корректные индексы —
    страница открывается быстро даже при кратном росте объёма.

  - Изолированный публичный API: отдельный API-gateway для партнёров с
    аутентификацией, rate limiting, квотами и версионированием; отдельный
    масштабируемый сервис приёма заказов; расчёт цены — отдельный сервис.
    Партнёрский трафик больше не влияет на работу операторов.

  - Развязанные данные: CRM API не ходит в Shop DB напрямую; взаимодействие
    систем — через API и события, чёткое владение данными.

  - Ускоренная поставка: пирамида автотестов и автоматизированный E2E в CI,
    автодеплой в release/prod с канареечными выкатками, фиче-флагами и быстрым
    откатом. Релизы перестают задерживаться на недели.

Это эволюционное движение существующего решения (не переписывание): те же три
приложения, но надёжный обмен, наблюдаемость, масштаб и изоляция публичного API.

5.2. ЕСЛИ МОЖНО ВЫПОЛНИТЬ ТОЛЬКО ТРИ ПУНКТА ЗА ПОЛГОДА

Выбираю I-1, I-2, I-3. Почему именно они:

  1) I-1 — Наблюдаемость + мониторинг жизненного цикла и SLA заказа.
     Почему первым: главная бизнес-боль — «заказы теряются/зависают, узнаём от
     клиента через месяцы». Пока мы не ВИДИМ, где заказ умирает, любые правки —
     вслепую. Инициатива дешёвая и быстрая, даёт немедленную пользу (алерт на
     просрочку SLA и на застрявшие заказы прекращает потерю контрактов «по-тихому»)
     и служит фундаментом для всех остальных решений и для заданий 2–5 спринта.

  2) I-2 — Надёжный асинхронный поток заказов.
     Почему вторым: это КОРЕНЬ проблемы «заказ пропал» у B2C и партнёров.
     Негарантированная доставка + отсутствие идемпотентности и outbox напрямую
     приводят к молчаливой потере. Гарантированная доставка, outbox/inbox, DLQ и
     ретраи останавливают утечку заказов и напрямую защищают выручку и контракты.

  3) I-3 — Масштабирование сервисов и БД + ускорение дашборда MES.
     Почему третьим: нагрузка растёт линейно, а после открытия API был всплеск;
     при одном инстансе и одной БД мы упрёмся в потолок независимо от надёжности.
     Горизонтальный масштаб и read-реплики снимают ограничение роста, а модель
     чтения + кеш + keyset-пагинация чинят ежедневную боль операторов (медленный
     дашборд), от которой зависит их оплата.
