ЗАДАНИЕ 5. АРХИТЕКТУРНОЕ РЕШЕНИЕ ПО КЕШИРОВАНИЮ

Справочный документ (ADR): зачем кеш, что кешируем, каким паттерном, как
инвалидируем. Опирается на Задание 1 (инициатива I-3: ускорение дашборда MES).

======================================================================
0. АНАЛИЗ: ЧТО ИМЕЕТ СМЫСЛ КЕШИРОВАТЬ
======================================================================
Симптомы: первая страница MES (дашборд «заказы в работе по статусам») грузится
медленно. Фильтр по статусам и пагинация не помогли. Операторам критично видеть
самые новые заказы первыми — от этого зависит их оплата («кто взял, тот и получил»).

Почему тормозит (из Задания 1, C1/C2 и B2):
  - чтения дашборда идут в ЕДИНСТВЕННУЮ ноду MES DB и конкурируют с записью
    (статусы меняются постоянно из очереди и от операторов);
  - тяжёлый агрегирующий запрос «список по статусу, свежие сверху» на растущей
    таблице; вероятна offset-пагинация и нехватка индексов;
  - нагрузка растёт линейно → запрос деградирует со временем.

Что кешируем (кандидаты, по убыванию пользы):
  1) ГЛАВНОЕ: read-модель дашборда — список заказов по статусу, отсортированный
     «новые сверху», постранично. Очень частое чтение, одинаковое для многих
     операторов → идеальный кандидат.
  2) Опционально: результат расчёта цены (PRICE_CALCULATED) — если для одного
     заказа/модели он запрашивается повторно (CPU-heavy операция).
  3) Опционально: справочные данные (каталог/материалы) — редко меняются.
  Фокус решения — пункт 1 (именно он про боль операторов и скорость страницы).

Что НЕ кешируем: операцию «взять заказ в работу» (это запись с гонкой за один
заказ — решается блокировкой/атомарным UPDATE в БД, а не кешем); финансово
критичные операции чтения-для-записи.

======================================================================
1. МОТИВАЦИЯ
======================================================================
Зачем кеширование:
  - Снять нагрузку чтения с единственной ноды MES DB и убрать конкуренцию
    чтения с записью → страница дашборда открывается быстро (цель: p95 < 200 мс
    вместо секунд).
  - Держать скорость при линейном росте заказов (кеш в памяти масштабируется
    независимо от БД).
  - Дать операторам быстрый доступ к «самым новым заказам» → прямая связь с их
    оплатой и скоростью взятия заказов в работу.
  - Косвенно ускорить выполнение заказа: операторы быстрее видят и берут новые
    заказы → меньше простоя в пайплайне.

Элементы, включаемые в кеширование:
  - список заказов по статусам (дашборд MES) — основной объект;
  - (опц.) результаты расчёта цены и справочники.

Метрики решения, на которые повлияет кеш:
  Технические: p95/p99 времени ответа дашборда ↓; число/латентность запросов к
  MES DB ↓; cache hit ratio (цель > 90% на списках); нагрузка (CPU/IO) БД ↓.
  Бизнесовые: время до взятия нового заказа оператором ↓; удовлетворённость
  операторов и клиентов скоростью ↑.

======================================================================
2. ПРЕДЛАГАЕМОЕ РЕШЕНИЕ
======================================================================
2.1. КЛИЕНТСКОЕ ИЛИ СЕРВЕРНОЕ КЕШИРОВАНИЕ
Выбор: СЕРВЕРНОЕ (общий кеш в памяти — Redis), НЕ клиентское. Почему:
  - Дашборд — общий для многих операторов, и всем нужны ОДНИ И ТЕ ЖЕ свежие
    «новые сверху» заказы. Клиентский кеш в браузере у каждого свой → один
    оператор видел бы устаревший список и «уводил» бы заказ, который уже взят
    (гонка «кто первый взял», от которой зависит оплата). Недопустимо.
  - Серверный общий кеш даёт единую согласованную картину и мгновенную
    инвалидацию для всех при смене статуса.
  - MES API планируется масштабировать горизонтально (Задание 1, I-3) →
    нужен ВНЕШНИЙ общий кеш (Redis), а не in-process кеш каждого инстанса
    (иначе рассинхрон между инстансами).
Клиентское кеширование оставляем только для статики фронта (JS/CSS, HTTP-кеш) —
это не про данные заказов.

Технология: Redis (in-memory, общий для всех инстансов MES API, быстрый,
поддерживает TTL и атомарные операции для версионной инвалидации).

2.2. ПАТТЕРН СЕРВЕРНОГО КЕШИРОВАНИЯ: Cache-Aside
Выбор: CACHE-ASIDE (lazy loading). Приложение само читает из кеша, при промахе
идёт в БД и кладёт результат в кеш; при изменении — инвалидирует.

Почему Cache-Aside:
  - Нагрузка read-heavy (дашборд читают много и часто) — классический сценарий
    для Cache-Aside.
  - Отказоустойчивость: если Redis недоступен, приложение просто читает из БД
    (деградация скорости, но не отказ). Кеш не на критическом пути записи.
  - Кешируем ПРОИЗВОДНЫЙ АГРЕГАТ (список по статусу+страница), а не отдельную
    запись — Cache-Aside это удобно поддерживает.

Почему не другие паттерны:
  - Write-Through: запись идёт «сквозь» кеш в БД, кеш всегда свежий. Но у нас
    кешируется СПИСОК, а пишется отдельный заказ; на каждую запись пришлось бы
    пересобирать все затронутые страницы списка в кеше — дорого и сложно. Плюс
    записи приходят из РАЗНЫХ источников (оператор, consumer очереди, CRM) — не
    все идут «через кеш». Записи стали бы медленнее без явной пользы для списков.
  - Refresh-Ahead: кеш проактивно обновляется до истечения TTL для «горячих»
    ключей. Полезно как ДОПОЛНЕНИЕ для самой горячей первой страницы, но как
    основной паттерн — сложнее, тратит ресурсы на обновление даже ненужных
    данных и не отменяет необходимости инвалидации при изменении. Оставляем как
    возможное улучшение (см. раздел 3, Решение 2), не как базу.

2.3. SEQUENCE DIAGRAM (операции чтения списка и записи статуса)
Полные диаграммы (Mermaid, рендерятся): Task5/sequence-diagrams.md
Сущности: Оператор → MES(React) → MES API(C#) → Redis(кеш) → MES DB(PostgreSQL),
плюс RabbitMQ как источник событий смены статуса.

  (1) ЧТЕНИЕ СПИСКА — Cache-Aside:
    Оператор → MES → MES API:  GET /orders?status=S&cursor=C
    MES API → Redis:           GET orders:ver:{S}         -> version N
    MES API → Redis:           GET orders:list:{S}:vN:{C}
      ├─ HIT:  Redis → MES API: список  → ответ из кеша (быстро)
      └─ MISS: Redis → MES API: nil
               MES API → MES DB: SELECT ... WHERE status=S
                                 ORDER BY created_at DESC (keyset по cursor)
               MES DB → MES API: строки
               MES API → Redis:  SETEX orders:list:{S}:vN:{C} TTL=30s
               MES API → MES:    ответ из БД + прогрев кеша
    MES → Оператор: новые заказы сверху

  (2) ЗАПИСЬ СТАТУСА — программная инвалидация:
    Источник (оператор ИЛИ consumer очереди) → MES API: сменить статус old→new
    MES API → MES DB:  UPDATE orders SET status=new WHERE id=? (транзакция)
    MES API → RabbitMQ: publish order.status_changed (через outbox)
    MES API → Redis:   INCR orders:ver:{old}   (сдвиг версии старого статуса)
    MES API → Redis:   INCR orders:ver:{new}   (сдвиг версии нового статуса)
    → все старые страницы vN этих статусов больше не читаются и истекают по TTL;
      следующее чтение = MISS → перечитывает свежие данные и прогревает кеш.

2.4. СТРАТЕГИЯ ИНВАЛИДАЦИИ КЕША
Выбор: ПРОГРАММНАЯ (событийная) инвалидация по версии статуса + короткий TTL
как страховка.

Как работает:
  - Ключ списка версионируется: orders:list:{status}:v{version}:{cursor}, где
    version хранится в orders:ver:{status}.
  - При смене статуса заказа приложение делает INCR версии затронутых статусов
    (старого и нового). Это МГНОВЕННО «инвалидирует» все страницы этих статусов
    без удаления/сканирования множества ключей (важно: SCAN/KEYS по Redis дорог).
  - Короткий TTL (напр. 30–60 с) — страховка на случай пропущенного события и
    для авто-очистки протухших версий.
Почему подходит: смена статуса — дискретное событие, которое мы и так публикуем
(order.status_changed). Привязать инвалидацию к нему — точно и своевременно, при
этом операторы почти сразу видят изменения (нет застревания на устаревшем списке).

Почему не другие стратегии (сравнение):

  Стратегия            | Плюсы                     | Минусы / почему не как основа
  ---------------------|---------------------------|------------------------------------
  Временная (TTL)      | Проще всего; не нужен     | Компромисс «свежесть vs нагрузка»:
  только               | код инвалидации          | большой TTL = операторы видят
                       |                          | старое (уводят взятые заказы);
                       |                          | малый TTL = много промахов, БД
                       |                          | снова под нагрузкой. В одиночку
                       |                          | не даёт нужной свежести.
  По ключу (точечно    | Точное удаление          | Список разбит на МНОГО ключей
  удалять затронутые   | конкретных записей       | (статус×страницы). Один новый
  ключи)               |                          | заказ влияет на первую страницу
                       |                          | статуса; вычислять и удалять все
                       |                          | затронутые ключи сложно, легко
                       |                          | ошибиться → рассинхрон.
  Программная +        | Точно (по событию),      | Нужен код инвалидации и
  версионирование      | своевременно, дёшево     | дисциплина «публиковать событие
  (ВЫБРАНО)            | инвалидирует все страницы| на каждое изменение». Приемлемо —
                       | статуса разом; TTL как   | событие у нас уже есть.
                       | подстраховка             |

Итог: временная — недостаточно свежа; по-ключу — сложна и хрупка на списках;
программная по версии + TTL — точна, дёшева и устойчива. Её и берём.

======================================================================
3. ДОПОЛНИТЕЛЬНО: ДВА ВАРИАНТА РЕШЕНИЯ И ЗАКЛЮЧЕНИЕ
======================================================================
Возможны два решения; сопоставим их.

  Решение 1: Redis + Cache-Aside поверх текущей MES DB
    Описание: кеш-слой в MES API поверх существующей БД; ключи-списки по статусу,
    программная инвалидация по версии + TTL. Диаграммы — раздел 2.3 /
    sequence-diagrams.md.
    Плюсы: быстро внедрить; минимальные изменения схемы; сразу снимает нагрузку
      чтения; отказоустойчиво (Redis упал → читаем БД).
    Минусы: при каждом промахе всё ещё тяжёлый запрос к БД; кеш хранит агрегаты,
      собранные тем же тяжёлым запросом; не устраняет корневую тяжесть запроса.

  Решение 2: CQRS — отдельная денормализованная read-модель
    Описание: по событиям order.status_changed поддерживаем готовую к чтению
      модель дашборда (в Redis-структурах/отдельном read-хранилище или
      materialized view). Запись обновляет read-модель асинхронно (по сути
      write-behind в модель чтения); чтение бьёт только в неё.
    Плюсы: чтение максимально дёшево (данные уже в нужной форме); нет тяжёлого
      агрегирующего запроса даже при промахе; лучше всего масштабируется под рост.
    Минусы: сложнее (нужно строить и поддерживать проекцию, обрабатывать
      eventual consistency и переигрывание событий); дольше внедрять.

  Сопоставление:
    Критерий              | Решение 1 (Cache-Aside) | Решение 2 (CQRS read-модель)
    ----------------------|-------------------------|-----------------------------
    Скорость внедрения    | Высокая                 | Низкая (больше работы)
    Сложность             | Низкая                  | Высокая
    Разгрузка БД чтения   | Высокая                 | Очень высокая
    Тяжесть запроса при   | Остаётся (на MISS)      | Устранена
    промахе               |                         |
    Масштабируемость      | Хорошая                 | Отличная (под линейный рост)
    Консистентность       | Просто (инвалидация)    | Eventual (нужно продумать)

ЗАКЛЮЧЕНИЕ:
Начинаем с Решения 1 (Redis + Cache-Aside + программная инвалидация по версии).
Оно быстро и дёшево закрывает боль операторов «медленный дашборд» и снимает
нагрузку с единственной ноды MES DB, оставаясь отказоустойчивым. По мере
дальнейшего роста нагрузки эволюционируем к Решению 2 (CQRS read-модель) — это
согласуется с инициативой I-3 из Задания 1 (модель чтения + read-реплики). Таким
образом получаем быструю пользу сейчас и ясный путь развития без переписывания.
